## 7. Blocking design finding CR-BOOTSTRAP-DESIGN-001 (circular trust)

```
Finding ID     : AUCDEV023-CR-BOOTSTRAP-DESIGN-001
Classification : HARNESS/PROTOCOL GOVERNANCE DESIGN DEFECT
                 / CIRCULAR TRUST
                 / TARGET_UNDER_AUDIT_USED_AS_AUTHORITY_ROOT
Support        : OBSERVED_DESIGN_FACT + TRUST-BOUNDARY INFERENCE
Status         : BLOCKING — DESIGN REVISION REQUIRED
```

**Observed design fact**: the proposed OPTION D-1 architecture (design
record §13, §22) assigns the frozen qh target
`d4d584ffa47ad2848268ba947247f81a845b2322` the role

> "PLANE 1 — CONTROL/AUTHORITY PLANE (the frozen qh harness at
> `d4d584ff`, unmodified)"

and states that Plane 1 performs:

> "EVERY authority decision and every zero-provider gate."

with the authority model "qh operator root + one-shot process-bound
attempts + operator-held transport launch".

**Trust-boundary inference**: the frozen qh harness is itself the
object whose trustworthiness the bootstrap independent audit must
establish. Therefore the independent audit MUST NOT require correctness
of that target as the root of auditor execution authority. This is
CIRCULAR TRUST. The target may be:

- audit subject;
- evidence source;
- test/rehearsal subject;
- deterministic signal producer.

It may NOT be the sole root that authorizes, denies, or consumes the
independent auditor's networked paid inference launch. A malicious or
materially defective target must not be able to obtain authority over
the process that independently reviews it.

## 9. Blocking design finding CR-BOOTSTRAP-DESIGN-002 (cross-plane one-shot launch not mechanically enforced)

```
Finding ID     : AUCDEV023-CR-BOOTSTRAP-DESIGN-002
Classification : HARNESS/PROTOCOL GOVERNANCE DESIGN DEFECT
                 / CROSS_PLANE AUTHORITY
                 / NETWORKED LAUNCH SINGLE-USE NOT MECHANICALLY ENFORCED
Support        : OBSERVED_DESIGN_FACT
Status         : BLOCKING — DESIGN REVISION REQUIRED
```

**Observed design fact**: the proposed plane binding (design record
§13 "Plane binding"; §15) says:

- each auditor attempt's qh grant id + attempt id are embedded in the
  transport FDR;
- the engagement ledger records the inference-capable CLI exec;
- the transport launch invocation is operator-held (never
  controller-held);
- pre/post launch captures (argv, environment digest, timestamps) make
  a second launch of the same attempt mechanically **DETECTABLE** —
  classified `UNAUTHORIZED_RETRY_AFTER_PREEXEC` (L-03) — with §15
  recording Plane-2 second-launch handling as "classified unauthorized
  retry if attempted (pre/post captures)".

**Detectable is not PREVENTED.** The qh one-shot supervisor serves
exactly one request on Plane 1, but it CANNOT mechanically prevent a
second NETWORKED Plane-2 exec, because the networked auditor process is
explicitly OUTSIDE the qh no-egress protected launch (the frozen
trusted-spec schema REQUIRES `noegress.required = true` — §11). This
risks recreating the historical RC-2 failure class:

```
UNAUTHORIZED_RETRY_AFTER_PREEXEC_BOUNDARY_FAILURE
```

on the plane where the paid inference actually occurs.

## 10. Required correction for DESIGN-002 (target-independent single-use launch capability)

The revised design must specify a TARGET-INDEPENDENT SINGLE-USE LAUNCH
CAPABILITY with these required properties:

- minted ONLY by the external bootstrap authority (§8);
- exact event + auditor role + attempt + frozen transport binding;
- inaccessible to the controller as forgeable ordinary state;
- consumed atomically BEFORE the inference-capable networked auditor
  process exec;
- ONE successful consumption only;
- replay mechanically refused;
- copied token mechanically refused or ineffective;
- wrong transport/binding refused;
- wrong role refused;
- wrong controller/process refused where process binding is used;
- failed PREEXEC state cannot silently re-use the capability;
- replacement requires NEW explicit operator authority and a NEW
  capability.

The enforcement MUST happen in the networked launch path itself. The
ledger and pre/post captures remain OBSERVABILITY EVIDENCE ONLY — they
cannot be the authority root.

## 11. Blocking design finding CR-BOOTSTRAP-DESIGN-003 (networked provider credential custody not established)

```
Finding ID     : AUCDEV023-CR-BOOTSTRAP-DESIGN-003
Classification : HARNESS/PROTOCOL GOVERNANCE DESIGN DEFECT
                 / NETWORKED PROVIDER CREDENTIAL CUSTODY
                 / CROSS_PLANE MATERIALIZATION GAP
Support        : OBSERVED_SOURCE_FACT + OBSERVED_DESIGN_FACT
Status         : BLOCKING — DESIGN REVISION REQUIRED
```

**Observed source fact** (frozen target `d4d584ff…`, read byte-wise
this session, never executed):

- `qh/trusted_spec.py` REQUIRES `noegress` for every protected launch:
  `TEMPLATE_NOEGRESS_MUST_BE_REQUIRED` (template validation) and
  `SPEC_NOEGRESS_MUST_BE_REQUIRED` (spec validation) raise unless
  `noegress.required` is true. Therefore the real provider-capable
  networked auditor CANNOT be a qh protected launch.
- `qh/custody.py` holds credential bytes ONLY in a sealed memfd inside
  the (qh) supervisor process, sourced ONLY from an operator-held
  pipe/memfd channel, with child-only materialization inside the
  SUPERVISED (qh boundary) child path, and teardown closing the memfd.
- `qh/adapters.py` defines materialization targets INSIDE the qh
  boundary layout: `codex_chatgpt_oauth_v1` →
  `/run-qh/codex-home/auth.json`; `claude_firstparty_oauth_v1` →
  `/run-qh/claude-config/.credentials.json` (mode 0600).

**Observed design fact**: the proposed design (§12 "Credential
governance") states operator/root custody + boundary-local
materialization (the "qh custody channel pattern") and Plane-2
role-minimal auth, but does NOT define the TARGET-INDEPENDENT
mechanical custody path from the operator secret source to the
NETWORKED external auditor child. The proposed networked transport
cannot automatically inherit the qh custody property — the qh custody
mechanism materializes inside qh-supervised no-egress children, which
the networked auditor by definition is not.

## 12. Required correction for DESIGN-003 (mechanical custody, independent of the qh target)

The revised external bootstrap authority/transport must define REAL
credential custody MECHANICALLY. Required properties:

- credential bytes enter ONLY through the operator-held capability;
- NOT argv;
- NOT environment;
- NOT an ordinary persistent file;
- NOT controller-readable;
- NOT hashed into evidence;
- NOT logged;
- target qh code does NOT receive the plaintext;
- the external bootstrap authority holds the bytes only in
  non-dumpable/sealed process state where supported/required;
- EXACTLY the authorized provider role receives it;
- materialization occurs ONLY inside the final networked auditor
  boundary;
- irrelevant role credential ABSENT;
- child-side home is ephemeral/writable-at-init as required;
- teardown removes the materialized plaintext;
- the controller cannot reproduce a provider-capable launch;
- a fake/replayed launch capability cannot obtain the credential.

Provider materialization FORMATS may reuse the two evidence-supported
layouts (`codex_chatgpt_oauth_v1`, `claude_firstparty_oauth_v1`), but
the custody IMPLEMENTATION must be INDEPENDENT of the qh target. NO
real credential execution is authorized in the design revision.

## 14. Revised architecture direction (three logical roles)

The next design should converge toward THREE LOGICAL ROLES, even if
implemented by two physical packages:

**A. EXTERNAL BOOTSTRAP AUTHORITY** — target-independent; minimal;
operator-controlled; one-shot launch/custody authority.

**B. NETWORKED AUDITOR TRANSPORT** — frozen event package; consumes the
external authority's one-shot capability; materializes the role-minimal
credential only after ALL gates; runs the external auditor.

**C. FROZEN QH TARGET** — audit subject; read-only evidence; may be
exercised in local/no-provider rehearsal; NEVER root authority for its
own independent review.

The next design must MINIMIZE new trusted code in A.
