## 6. Blocking finding — receipt canonical context

`AUCDEV023-CR-G3-PKGIDENT-002-RECEIPTCTX-001` — **RECEIPT_ONE_SHOT_AND_GRANT_CONTEXT_ARE_NOT_CANONICALLY_BOUND**

Classification: HARNESS / AUTHORITY-PROTOCOL IMPLEMENTATION DEFECT WITH LATENT DESIGN-COMPLETENESS EXPOSURE. Support: OBSERVED SOURCE FACT / FILESYSTEM SEMANTICS. Status: OPEN / BLOCKING_G3_PACKAGE_BINDING_CONSIDERATION / REMEDIATION_REQUIRED / NOT_A_FROZEN_TARGET_PRODUCT_DEFECT.

Observed implementation facts (each independently re-derived data-only from the exact published binding.py this session): `write_package_binding_receipt(root, record)` accepts a CALLER-SELECTED `root`; the deterministic filename is keyed by `grant_identity` only (`receipt_name(grant_identity)` = grant_identity + suffix), but the `O_EXCL` create is scoped to THAT selected directory (dir_fd of the opened root). Therefore the SAME exact `grant_identity` can receive TWO separate receipt files under two different valid owner-controlled roots. Independent filesystem reproduction confirmed this session in a throwaway /tmp world: the identical deterministic O_EXCL filename was created successfully once in EACH of two distinct directories (both directories valid under the namespace checks), while the same-root duplicate was refused with EEXIST — so O_EXCL one-shot semantics are caller-selected-root LOCAL, not global to the exact `grant_identity`. This violates the accepted protocol property EXACTLY ONE receipt per `grant_identity` unless ONE canonical receipt namespace is mechanically bound.

The implementation also does NOT mechanically prove that the supplied root IS the ONE dedicated package-binding receipt namespace, NOR that it is disjoint from the frozen runtime/accounting namespace, NOR that it is disjoint from Git-tracked operative state (the namespace opener checks only: real directory, no symlink, owner uid, not group/world-writable).

Further, the receipt record carries `operator_authority_id`, while `verify_package_binding_receipt(root, grant_identity, package_sha256)` does NOT derive or cross-check that value against the exact grant bytes whose digest is `grant_identity` (the verify body cross-checks ONLY `grant_identity` and `package_sha256` equality; machine-verified this session). Thus the source primitive does not yet enforce the complete grant/receipt context relation.

G4 MUST remain forbidden. This finding BLOCKS G3 package-binding consideration; PKGIDENT-002 requires implementation remediation (Section 18).
