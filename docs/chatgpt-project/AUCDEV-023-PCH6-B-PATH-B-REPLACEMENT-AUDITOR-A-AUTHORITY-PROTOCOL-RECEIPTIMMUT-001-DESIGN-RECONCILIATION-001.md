## 9. Clarification 1 — content-identity enforcement vs inode continuity (normative restatement; interpretive of the published design; changes NO contract)

(a) The pinned ORIGINAL receipt identity is a CONTENT identity: (`receipt_path`, `receipt_sha256`, `receipt_size`) plus the grant/package/G7/namespace cross-bindings. (b) The receipt FILE's own st_dev/st_ino is NOT a pinned identity and is NOT verified by G10/G11; RI-T05's "inode identity irrelevant by design" applies to the receipt FILE generally, not only to the same-inode rewrite row. (c) Section 15's "unlink + replacement inode" and "same canonical pathname with new inode" rows, RI-T04, and G10.4's "replacement" refusal are hereby read and normatively clarified as CONTENT-substitution detections: the refusal basis is that the re-read bytes are NOT the ORIGINAL canonical bytes (byte/SHA/size inequality, canonicalization mismatch, or semantics mismatch). A re-created file at the canonical path whose bytes are byte-identical to the ORIGINAL canonical bytes violates NO pinned identity, is NOT detectable by the pinned identities, and REQUIRES no detection under the accepted operator direction: it leaves every pinned fact and every acceptance decision unchanged. (d) The `receipt_namespace_st_dev`/`receipt_namespace_st_ino` fields remain exactly what they are — the NAMESPACE DIRECTORY object pin (verifier-side facts of the verified G7 context) — and must never be read as, relabeled as, or "fixed" into the receipt file's object identity. (e) IF a future operator decision should require receipt FILE object continuity as an independent invariant (e.g., forensic chain-of-custody of the file object itself), that is a NEW contract requirement: it CANNOT be satisfied inside the accepted closed-world 24-field publication schema (it would need a receipt-file st_dev/st_ino field or equivalent) and would therefore require DESIGN_REBIND via an explicit operator decision. This reconciliation adds NO such field, builds NO such machinery, closes NOTHING on it, and records the boundary only. It is further noted (analysis, not decision): even such a pin would be a POST-creation stat of an owner-writable object — a weaker derivation class than the G10.1/G10.2 verified-inputs construction the accepted pattern deliberately chose; and chmod/permission state remains defense-in-depth only, never the proof.
